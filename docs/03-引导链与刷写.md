# 引导链、签名与刷写（复现时最危险的部分）

> 这一篇里每一条「不要」都是踩过的坑。**动手前至少读完第一节和最后一节。**

## 一、分区布局（A/B 双槽）

扇区 4096 B。**引导链区是红线，一个字节都不要碰。**

| 分区 | 当时放了什么 |
| --- | --- |
| `boot_a` | Linux 内核（主线 7.2.7 `dr_mode=host`，AOSP testkey 签名，96 MiB 填满） |
| `boot_b` | 原厂 Android（未改动）—— `fastboot set_active b` 秒切保底 |
| `init_boot_a` | 探测/分流 init（原厂 init 改名 `/init.orig` 随包保留；原备份 `init_boot_a_now.img`） |
| `vendor_boot_a` | 本项目 elden dtb 版（插了 SunP identity + `__symbols__`） |
| `dtbo_a` | 原厂（换回后行为一致，已确认不是失败原因） |
| `vbmeta_a` | 原厂未动（vbmeta 是链式结构，只信任 boot 分区自己的 footer，**不校验 boot hash**） |
| `recovery_a` | TWRP 3.7.1_16-TB322FC（recovery 分区不校验签名，可当测试通道） |
| `misc`（sda7） | 已清零（`misc-zero.img`），BCB 不再粘住启动 |
| `userdata`（sda16，约 449 GB） | Debian 13.7 rootfs，ext4，`resize2fs` 扩到约 443 G |
| `rawdump`（sda14，256 MB） | 偏移 30 MB 处放 rootfs 备份（分区头是内存转储区 `Raw_Dmp!`，不能直接建文件系统） |
| `lenovocust`（sda3，300 MB ext4） | 第二份 rootfs `/y700-rootfs.img` |
| `pstoredump`（sda15，128 MB） | 内核日志落盘通道（魔数 `Y700LINUXLOG`） |
| `super` | 原厂动态分区，**未动**（动它会触发 AVB 拒绝） |
| modem / persist / proinfo / ddr / cdt / 引导链区（sde 78 个 + sdb/sdc/sdd/sdf） | 原厂未动 |

> **绝对不要改 GPT**。当时的想法是「缩 `userdata` 250 G 新建 `linuxroot`」，
> 结果：原厂 GPT 条目 CRC 字段指向另一份空表，照抄即错 → 整机卡 fastboot，
> 刷回原厂 GPT + 全量包才救回来。**正确做法是只改分区内的文件系统。**

## 二、解锁

两条路：

1. 官方：`http://www.zui.com/iunlock`（每账号每年限 3 台）
2. 本机定制：`fastboot getvar all` 取 `sn1`+`sn2` → 改写 `sn.img` 里的序列号 → `fastboot flash unlock sn.img` → `fastboot flashing unlock`

一次性、不可逆、失去保修。

## 三、备份（先备份，再动手）

### 3.1 必须有的「保命符」

身份分区，共 13 个约 50 MB：

```
proinfo  persist  modemst1  modemst2  fsg  fsc  devinfo
keystore  frp  lenovolock  ssd  uefivarstore  secdata
```

其中 **`persist` 不可再生**（传感器与相机校准），丢了相机/传感器永远不准。

### 3.2 引导链五件套

```
boot_a  boot_b  init_boot_a  init_boot_b  vendor_boot_a  vendor_boot_b
dtbo_a  dtbo_b  vbmeta_a  vbmeta_b  misc(全零)
```

用 `fastboot` / `dump` 或刷机匣回读导出。当时的做法是刷机匣导出 17 分区 / 1396 MB。
**每次刷写前确认 `boot_a_now.img` 和五件套还在。**

## 四、AVB 与签名（这一节最重要）

### 4.1 结论先行

**不需要联想的 OEM 私钥。** 用 **AOSP 公开 testkey** 签的 `boot.img` 能过 ABL。

### 4.2 为什么

- `vbmeta` 是**链式**结构，只校验它自己列出的分区描述符；**不校验 boot 的 hash**
- ABL 真正的门是：boot 分区的 AVB footer 里**必须有 prop 描述符**（`com.android.build.boot.*`）
- 缺了 prop → 防降级检查判成「版本 0」→ 拒收（当年误判为「签名墙」）
- 补齐 3 个 prop + salt + rollback_index 后，testkey 直接过

### 4.3 实测参数

```bash
avbtool add_hash_footer \
  --image boot.img \
  --partition_size 100663296 \              # 96 MiB，等于 boot 分区大小
  --partition_name boot \
  --key aosp-testkey_rsa4096.pem \
  --algorithm SHA256_RSA4096 \
  --hash_algorithm sha256 \
  --rollback_index 1738713600 \
  --salt 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2b \
  --prop com.android.build.boot.os_version:15 \
  --prop com.android.build.boot.fingerprint:Lenovo/TB322FC_PRC/TB322FC:16/... \
  --prop com.android.build.boot.security_patch:2025-02-05
```

工具用法铁律：

- **`add_hash_footer`**，不是 `add_hashtree_footer`（用反会得出「签名墙不可越」的错误结论）
- 换 root key 会**全拒**，不要试
- `boot.img` 头必须是 **v4**（v2 会被 ABL 拒）

### 4.4 AOSP testkey 从哪来

AOSP 源码树：`build/make/target/product/security/testkey_rsa4096.pem`。
公钥 sha1 当时核过：`2597c218`。

> 含义：任何拿到这个公开 key 的人都能签一个「能启动」的镜像。所以这只是个人实验机方案，
> 不构成任何安全边界。

## 五、打包 boot.img

```bash
: > empty-ramdisk                       # 空 ramdisk（initramfs 已内嵌内核）
mkbootimg --header_version 4 \
  --kernel Image \
  --ramdisk empty-ramdisk \
  --os_version 15.0.0 --os_patch_level 2026-08 \
  --cmdline "$CMDLINE" \
  --output boot.img
```

cmdline 关键点：

- `root=PARTLABEL=userdata`（GEEKiDoS 原版写的是 `rootfs`，本机分区标签是 `userdata`，必须改）
- `console=tty0 fbcon=map:0 fbcon=font:TER16x32 loglevel=7`
- `bootconfig init=/init rdinit=/init ro panic=0 efi=noruntime`
- `usbcore.autosuspend=-1 fw_devlink=permissive`
- `arm-smmu.disable_bypass=0 clk_ignore_unused pd_ignore_unused regulator_ignore_unused`
- `initcall_blacklist=clk_disable_unused,regulator_init_complete,genpd_power_off_unused`
- `mem_sleep_default=s2idle`

## 六、刷写

```bash
# ① 零写入试跑（推荐；不改变任何分区，也不消耗 slot 重试额度之外的次数）
fastboot boot boot.img

# ② 确认能进系统、能 SSH 之后，再考虑写入
fastboot flash boot_a boot.img
fastboot set_active a
```

> 4 GB 以上的 raw 镜像必须先 `img2simg` 转 sparse（4 GB → 240 MB，5.6 秒刷完）。
> 直接刷 raw 会 `std::bad_alloc`。

## 七、ABL 重试额度（长期使用必看）

机制（2026-10-12 实测）：

- `fastboot set_active a` 会把 `slot-retry-count:a` 重置为 **7**
- 之后每次引导，**如果系统没有报告「启动成功」，计数减 1**
- Linux 侧从不报 → 7 次开机后 `slot-unbootable:a=yes` / `slot-retry-count:a=0` → 卡在 fastboot
- 卡住时**内容没坏**，一条 `fastboot set_active a` 就能续命

**自动化的正确做法**：装 `qbootctl`，启用 `qbootctl-mark-successful.service`，
每次到 `multi-user.target` 就把当前 slot 标成功（详见 `05-上游现状-2026-11.md`）。

## 八、回退与救砖

| 场景 | 做法 |
| --- | --- |
| 日常回 Android | `fastboot set_active b` → `reboot` |
| A 槽要重来 | 刷回五件套 + `misc` 全零 + `set_active a` + `reboot` |
| 卡 fastboot（被拉黑） | `fastboot set_active a`（重置计数） |
| BCB 写坏 | `fastboot boot boot_a_now.img` 进 Android → `adb shell su -c reboot` |
| 进 recovery | 唯一通道：Android 下 `adb reboot recovery` |
| 进 fastboot | 拔 USB → 电源 + 音量下长按 20 秒 |
| 进 EDL(9008) | 关机 → 音量上 + 插线 |
| 整机卡死/黑砖 | 9008 + `qdl`（或刷机匣）刷回原厂分区；最坏刷全量官方包 |

**三层保底**：① fastboot ② EDL/9008 ③ 官方全量线刷包。

## 九、红线清单

1. **不改 GPT。**
2. **不碰引导链区**（sde 78 个 + sdb/sdc/sdd/sdf）。
3. 刷写前确认备份在手（五件套 + 身份分区）。
4. 「引导器接受镜像」≠「引导成功」：判断成功要靠**屏幕 / 串口 / pstore** 三条独立证据。
5. 一次只改一个变量；同一个坑试 3 次不成就换工具或停手。
6. 长对话里形成的「结论」要回读原始证据再确认 —— 本项目 36 条翻案里，多半是长上下文里推断被当成了实测。
